# FOTOIN

**Foto produk siap jualan, dari HP kamu.**

FOTOIN is a hybrid AI product-photography service for Indonesian UMKM (micro, small and
medium enterprises). A seller snaps a product with their phone, picks a category, and gets
back clean, marketplace-ready visuals in minutes — generated by AI, **checked by a human**
before delivery.

This repository contains the full web application: a Node.js/Express API and a React
frontend, running as an npm workspace monorepo.

---

## Why this exists

An UMKM seller sits between two bad options: blurry phone photos that kill conversion, or a
professional studio shoot they cannot afford or schedule. FOTOIN closes that gap.

| | Self-serve AI tools | Photo studio | **FOTOIN** |
|---|---|---|---|
| Cost | Subscription, USD-priced | Rp500k+ per session | **Rp15.000–Rp25.000 per pack** |
| Skill needed | Prompt writing, editing | None | **None — pick a category** |
| Turnaround | Minutes, unpredictable quality | Days | **1–6 hours, QA'd** |
| Output | Raw image, wrong size | Raw image | **Exact Shopee / Tokopedia / TikTok sizes** |
| Channel | Web app, English | In person | **WhatsApp + web, Bahasa Indonesia** |

### The four differentiators, and where they live in the code

| Differentiator | Implementation |
|---|---|
| **Hybrid service, not a tool** — a human QA's every batch before it ships | `server/src/services/review.service.js`, `web/src/pages/ReviewPage.jsx` |
| **Indonesia-native** — Bahasa UI, presets for 4 local verticals | `server/src/data/catalog.js` (`CATEGORIES`), all frontend copy |
| **Marketplace-ready output** — exact pixel specs, auto-cropped | `catalog.js` (`MARKETPLACES`), `server/src/services/image.service.js` |
| **WhatsApp-centric, non-subscription** — QRIS / e-wallet, per pack | `server/src/services/whatsapp.service.js`, `payment.service.js`, `catalog.js` (`PACKS`) |

## How the product works

```
  1. SNAP            2. SEND             3. GENERATE          4. REVIEW & DELIVER
  ┌─────────┐        ┌─────────┐         ┌──────────┐         ┌──────────────┐
  │ Phone   │  ───►  │ WhatsApp│  ───►   │ AI makes │  ───►   │ Human checks │  ───► WhatsApp
  │ photo   │        │ or web  │         │ variants │         │ then ships   │
  └─────────┘        └─────────┘         └──────────┘         └──────────────┘
                     + category          studio / lifestyle    marketplace sizes
                     + style             / flat-lay            per channel
```

The seller **never writes a prompt**. They choose a category (Kuliner, Fashion & Hijab,
Kerajinan, Skincare) and a style preset; the prompt and background treatment are ours.

### Order status machine

```
draft ──► menunggu_pembayaran ──► diproses_ai ──► menunggu_review ──► selesai
                                       ▲                 │
                                       └──── revisi ◄────┘
                    (any non-terminal state) ──► dibatalkan
```

`menunggu_review` is not optional — it is the product. Nothing reaches a seller that a
person has not looked at. (`REQUIRE_HUMAN_REVIEW=false` exists for load testing only.)

## Tech stack

| Layer | Choice | Why |
|---|---|---|
| API | Node.js 20+, Express 4, ES modules | Small, boring, easy to hand over |
| Images | [sharp](https://sharp.pixelplumbing.com/) | Fast native compositing + exact resizing |
| Validation | zod | One schema, seller-facing Bahasa error messages |
| Uploads | multer (disk storage) | Swap for S3/GCS in production |
| Storage | JSON file via `src/data/store.js` | Zero-install dev; repository interface ready for Postgres |
| Frontend | React 18, Vite 7, React Router 7 | Fast dev loop, no framework lock-in |
| Styling | One hand-written CSS file with design tokens | Every shipped rule is readable |

There is no database daemon, no Docker requirement and no API key needed to run the whole
thing end to end. The default `mock` image provider composites real output locally.

## Quick start

```bash
# Requires Node.js 20 or newer
git clone <this-repo> && cd fotoin
npm install

# Optional: both apps have working defaults, so this is only needed to change them
cp server/.env.example server/.env
cp web/.env.example web/.env

npm run dev
```

| Service | URL |
|---|---|
| Web app | http://localhost:5173 |
| API | http://localhost:4000 |
| Health check | http://localhost:4000/api/v1/health |
| Reviewer console | http://localhost:5173/review |

### Try the full loop in 60 seconds

1. Open http://localhost:5173 and click **Mulai Pesan**.
2. Upload any product photo, name the product, pick a category and a style.
3. Choose a marketplace and a pack, enter a name and a phone number, and create the order.
4. On the order page, click **Saya sudah bayar** (stands in for the payment webhook).
5. Watch the progress bar. When it flips to *Menunggu Cek Reviewer*, open
   **/review** in another tab.
6. Click any frame you consider bad to mark it rejected, then **Setujui & kirim**.
7. Back on the order page: the approved images are there, sized per marketplace, with
   download links. The WhatsApp message the seller would have received is printed in the
   server console and available at `GET /api/v1/messages`.

### Commands

| Command | Does |
|---|---|
| `npm run dev` | Runs API and web together with hot reload |
| `npm run dev:server` / `npm run dev:web` | Run one side only |
| `npm test` | Server test suite (unit + end-to-end pipeline) |
| `npm run build` | Production build of the web app into `web/dist` |
| `npm start` | Runs the API in production mode |

## Configuration

All variables have working defaults — the app runs with no `.env` at all. Full list in
[`server/.env.example`](server/.env.example) and [`web/.env.example`](web/.env.example).

| Variable | Default | Notes |
|---|---|---|
| `PORT` | `4000` | API port |
| `IMAGE_PROVIDER` | `mock` | `mock` needs no API key; see below to plug in a real model |
| `MOCK_GENERATION_DELAY_MS` | `2500` | Simulated AI latency, so the UI progress state is visible |
| `REQUIRE_HUMAN_REVIEW` | `true` | **Keep this on.** It is the differentiator |
| `REVIEWER_TOKEN` | `dev-reviewer-token` | Must match `VITE_REVIEWER_TOKEN` in the web app |
| `WHATSAPP_ENABLED` | `false` | When off, messages are logged and stored, not sent |
| `PAYMENT_PROVIDER` | `mock` | Issues a fake QRIS payload |
| `MAX_UPLOAD_MB` / `MAX_FILES_PER_ORDER` | `10` / `5` | Upload limits |

### Plugging in a real image model

`server/src/services/image.service.js` is the only file that talks to a generator. Implement
one function with this contract and point `IMAGE_PROVIDER` at it:

```js
async function generate({ sourcePath, style, order }) {
  // style.background and style.description carry the preset;
  // return a Buffer or a file path of the styled image.
}
```

The marketplace resizing step downstream is provider-agnostic, so exact output dimensions
keep working regardless of which model produces the image.

## Testing

```bash
npm test
```

29 tests across three files, no test framework dependency (`node:test` only):

- `tests/catalog.test.js` — catalog integrity: four verticals, unique style ids, pricing
  stays inside the Rp15.000–Rp25.000 band, packs improve monotonically with price.
- `tests/order.service.test.js` — phone normalisation, pack-limit validation, and the status
  machine (including that illegal jumps are refused).
- `tests/pipeline.e2e.test.js` — boots the real app on an ephemeral port and walks the whole
  journey over HTTP: upload → order → pay → generate → review → deliver, asserting that the
  rendered files match each marketplace's pixel spec, that the reviewer endpoint is
  staff-only, that rejected frames are withheld from the seller, and that a rejection
  re-enters the pipeline.

## Production checklist

This is a pilot-grade codebase. Before real sellers touch it:

- [ ] Replace `src/data/store.js` with Postgres (Prisma) — the interface already matches
- [ ] Move uploads and results to S3/GCS with signed URLs instead of local disk
- [ ] Replace the in-process queue in `pipeline.service.js` with BullMQ + Redis
- [ ] Real seller authentication (WhatsApp OTP), and real reviewer accounts with roles
- [ ] Drive payment settlement **only** from the provider webhook; delete `POST /orders/:id/pay`
- [ ] Verify the WhatsApp webhook signature (`X-Hub-Signature-256`)
- [ ] Rate limiting, request size limits at the edge, and structured logging
- [ ] Retention policy for seller photos, plus a privacy notice in Bahasa Indonesia
